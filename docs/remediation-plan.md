# خطة إصلاح وتنظيم مشروع CalmBoard

> الحالة: جاهزة للتنفيذ
> تاريخ الإعداد: 2026-07-27
> النطاق: إصلاح المشروع الحالي تدريجيًا دون إعادة بنائه من الصفر
> المرجع: البرومبت الرئيسي ومتطلبات القبول النهائية

## 1. الهدف

تحويل المشروع الحالي من نموذج أولي واسع الوظائف إلى منصة SaaS متعددة المستأجرين، آمنة، قابلة للاختبار والنشر، مع الحفاظ على الواجهة والوظائف القابلة لإعادة الاستخدام.

يجب تنفيذ المراحل بالترتيب. لا تبدأ مرحلة جديدة قبل نجاح معايير إغلاق المرحلة السابقة في CI.

## 2. قواعد التنفيذ

- لا يُسمح بإعلان أي وظيفة مكتملة إذا كانت محاكاة أو تعمل داخل الواجهة فقط.
- لا تُقبل أي Mutation دون مصادقة، Tenant Context، صلاحية، والتحقق من المدخلات.
- لا تُؤخذ `userId` أو `organizationId` من Body لتحديد هوية المنفذ أو نطاق صلاحياته.
- يجب إبقاء المشروع قابلًا للتشغيل في نهاية كل مرحلة.
- كل تغيير معماري مهم يُسجل في ADR داخل `docs/architecture/decisions`.
- كل إصلاح أمني مهم يحصل على اختبار Regression.
- تُستخدم Feature Flags لإخفاء الوظائف غير المكتملة.
- لا تُضاف مكتبة جديدة دون توثيق الحاجة والترخيص والحالة الأمنية.

## 2026-08-01 - فرض حدود الاستخدام من الخادم

أضاف الترحيل `0050_server_usage_limits.sql` عدادات الاستخدام الحالي للمقاعد والمشاريع والمهام وحجم المرفقات إلى `usage_limits` مع تعبئة أولية من البيانات الفعلية وقيد يمنع القيم السالبة. أصبح `max_seats` يساوي عدد المقاعد المختار في الاشتراك والمدفوع له، بدلاً من الحد الأعلى الذي تسمح الخطة بشرائه، بينما تستمر حدود المشاريع والمهام والتخزين من كتالوج الخطة. لا يحذف خفض الخطة موارد العميل القائمة، لكنه يمنع أي إنشاء أو استعادة جديدة ترفع الاستخدام فوق الاستحقاق الحالي.

تحدّث Triggers مستوى الأمر العدادات بفرق ذرّي واحد لكل مؤسسة بعد إدخال أو تحديث أو حذف المشاريع والمهام والمرفقات، وتستخدم transition tables حتى يبقى الإدخال المجمع سريعاً. أما المقاعد فتُعاد مزامنتها تحت قفل صف `usage_limits` من عدد المستخدمين النشطين المميزين عبر المؤسسة، ولذلك لا تحسب عضويات Workspaces المتعددة للمستخدم نفسه أكثر من مرة. تسلسل تحديث صف العداد يجعل طلبات المؤسسات المتزامنة تتنافس على قفل واحد؛ إذا أصبح العداد أعلى من الحد ترمي قاعدة البيانات خطأ مقيداً وتتراجع المعاملة كلها. تحوّل بوابة Nest هذا الخطأ إلى `409 usage_limit_exceeded` دون تمرير تفاصيل قاعدة البيانات الخام.

## 2026-08-04 - التحقق التشغيلي من الحاويات وبيئة Staging والمراقبة

صُححت حاويات الإنتاج بحيث يكون هدف API الافتراضي هو التطبيق لا migrator، وتعمل صور API وWorker بأوامرها الصحيحة وبمستخدم غير root. استُبدلت فحوص الصحة المعتمدة على أدوات غير موجودة داخل الصور بطلب Node مباشر، ووُحّد اتصال Worker بقاعدة البيانات مع دور الصيانة في Compose. أُعيد بناء صور API وWorker وWeb ونجحت حالاتها الصحية، ولم تظهر أنماط أخطاء في سجلات التشغيل.

كشف تشغيل WebKit عدم تطابق بين عنوان API المبني داخل الويب (`API_PUBLIC_URL=http://localhost:5500`) والمنفذ الثابت `4000:4000` في Compose، فكانت الواجهة تعرض `Load failed` عند التسجيل. أصبح منفذ المضيف `${API_PORT:-4000}` بينما يبقى منفذ الحاوية 4000، وبذلك يستخدم التطوير المحلي وCompose المصدر البيئي نفسه دون تغيير منفذ الخدمة الداخلي.

بعد وصول WebKit إلى API كشف اختلافاً ثانياً: كانت حاوية API المحلية تعمل بـ`NODE_ENV=production` فتضيف `Secure` إلى cookies رغم أن `APP_URL` محلي عبر HTTP، ولذلك لم يرسل WebKit cookie الخاص بـCSRF وأعيد `403 CSRF validation failed`. أضيف الضبط الصريح `AUTH_COOKIE_SECURE`: قيمته الافتراضية الآمنة في production وStaging هي `true`، بينما يضبطه Compose المحلي فقط إلى `false`. غطت ثلاث حالات وحدة سلوك القيمة الافتراضية والتجاوزين، ونجحت 126 حالة API وTypeScript. بعد إعادة بناء الصورة نجح مسار WebKit كاملاً 4/4، ثم Chromium 4/4.

نُقل Socket.IO إلى منفذ API نفسه بدلاً من منفذ داخلي منفصل غير مكشوف، وأصبح fallback في الويب مشتقاً من عنوان API. نجح اتصال Realtime الفعلي على منفذ API داخل Docker، كما أضيف حد زمني وتنظيف صريح لاتصال اختبار التكامل حتى لا تبقى العملية معلقة بعد النجاح.
